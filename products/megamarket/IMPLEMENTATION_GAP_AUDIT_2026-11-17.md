# ممیزی اجرایی و ماتریس شکاف MegaMarket

**تاریخ ممیزی:** 2026-11-17  
**نوع ممیزی:** فقط‌خواندنی؛ بدون تغییر دیتابیس، سرویس، تنظیمات یا ادغام کد  
**مبنای محصول:** `products/megamarket/PROJECT_SUMMARY_AND_DECISIONS.md`  
**مخزن کنترل:** `grinlife4-stack/TRADIX`  
**شاخه مبنای بررسی:** `main`، commit `92e82f760abae5147e853807efe37873da21ba07`

## 1. نتیجه اجرایی

MegaMarket مورد توافق، **موتور مستقل تصمیم‌گیری خرید برای مصرف‌کننده** است؛ نه فروشگاه، نه دراپ‌شیپینگ، نه بازار خریدوفروش داده.

داده برای بهتر کردن تصمیم خرید، سنجش کیفیت شواهد و اعلام صادقانه «اطلاعات ناکافی» لازم است. لازم نیست خود داده به مشتری فروخته شود. درآمد اولیه از Affiliate می‌آید، اما لینک تجاری باید بعد از رتبه‌بندی مستقل متصل شود و کمیسیون نباید در انتخاب یا رتبه اثر داشته باشد.

**نتیجه ممیزی:** سند محصول وجود دارد، اما MVP مورد توافق هنوز در `main` پیاده‌سازی نشده است. چند شاخه توسعه، یک موتور متفاوتِ فروشنده‌محور/دراپ‌شیپینگ ساخته‌اند. آن کدها نباید بدون بازطراحی و تطبیق با سند محصول وارد MegaMarket شوند.

## 2. تعریف و محدوده‌ای که باید حفظ شود

MVP مصوب:

1. یک دسته محصول و یک بازار جغرافیایی محدود.
2. دریافت داده فقط از فید فروشنده، شبکه Affiliate، API یا منبعی که مجوز استفاده از آن روشن و مستند است.
3. کاتالوگ استاندارد و تطبیق شناسه/گونه محصول.
4. جست‌وجو و فیلتر پایه بدون وابستگی به AI.
5. نمایش قیمت، موجودی و زمان آخرین به‌روزرسانی.
6. مقایسه ۲ تا ۳ محصول و در صورت امکان چند فروشنده.
7. نمایش منبع، تازگی و محدودیت شواهد؛ اعلام رسمی «شواهد ناکافی».
8. توصیه خرید، انتخاب جایگزین یا توصیه به نخریدن.
9. اتصال Affiliate پس از تصمیم و افشای رابطه مالی.
10. ثبت نسخه تصمیم و امکان ممیزی.

تحلیل نظرها فقط در صورت مجوز روشن و داده کافی فعال می‌شود. تشخیص قطعی نظر جعلی، مشاور همه‌فن‌حریف، تحلیل جهانی، یادگیری از خرید کاربران و جست‌وجوی سنگین خارج از MVP هستند.

### مغایرت ماهوی کدهای موجود

کد شاخه `product/mega-market-local-runner-v0-1` به‌جای تصمیم‌گیری خرید مصرف‌کننده، عمدتاً یک دروازه ارزیابی محصول برای **فروشنده/دراپ‌شیپر** است:

- هزینه تأمین‌کننده، ارسال، کارمزد بازار، پرداخت، تبلیغات، مالیات و ذخیره مرجوعی را محاسبه می‌کند.
- شواهدی مانند پیشنهاد تأمین‌کننده، مجوز ارسال مستقیم و انطباق تجاری را می‌طلبد.
- خروجی آن `eligible_for_manual_pilot` است، نه رتبه‌بندی مستقل برای خریدار.
- دریافت‌کننده گزارش فروش و ارزیابی حاشیه سود فروشنده است، نه مقایسه نیاز، ویژگی و ارزش خرید مصرف‌کننده.

بخش‌هایی مانند `Decimal` برای پول، شناسه GTIN، ثبت منشأ داده، تازگی شواهد و توقف در نبود مدرک می‌توانند الگوهای فنی قابل استفاده مجدد باشند؛ اما منطق تجاری فعلی با محصول مصوب یکی نیست.

در این شاخه‌ها، `SourceRegistry` فقط در حافظه اجرا می‌شود و تست‌ها از adapterهای جعلی استفاده می‌کنند. اتصال زنده به فید فروشنده، شبکه Affiliate یا API واقعی مشاهده نشد.

### وضعیت تست کدهای آزمایشی

آخرین CI مربوط به PR #30 موفق است: [run 44073175833](https://github.com/grinlife4-stack/TRADIX/actions/runs/44073175833)، با **۶۵ تست موفق** و اجرای دموی آفلاین.

این نتیجه فقط صحت مسیر آزمایشی مبتنی بر داده ساختگی را نشان می‌دهد. در خود دمو تصریح شده که مجوز منبع، فروش، مجوز تأمین‌کننده و بررسی انطباق همگی ساختگی‌اند؛ هیچ داده زنده، سفارش، پرداخت یا اتصال تجاری انجام نمی‌شود. بنابراین این CI، اعتبار بازار یا آمادگی تجاری MegaMarket را اثبات نمی‌کند.

## 5. وضعیت زیرساخت‌های متصل

### Neon

پروژه `TRADIX NEON` سه شاخه دارد:

- `production` — شناسه `br-lingering-hall-bdh0g9if`: بدون جدول کاربردی، بدون Function، بدون Neon Auth و بدون Realtime. AI Gateway فعال است؛ Object Storage فعال است ولی Bucket ندارد.
- شاخه مهاجرت `br-bitter-firefly-bd1jt928`: هفت جدول حافظه وجود دارد، اما شمار ردیف همه آن‌ها صفر است.
- شاخه دفتر کارخانه `br-still-river-bdh6nflp`: چهارده جدول دارد و داده آزمایشی کارخانه در آن ثبت شده است؛ یک Function با نام `memorygw` نیز deployment با وضعیت `completed` دارد.

در شاخه دفتر کارخانه، یک پروژه، یک مأموریت، یک task، یک attempt موفق، سه رویداد task، دو تصمیم و شش checkpoint مشاهده شد. آخرین checkpoint همچنان اجرای smoke testهای HTTP و تأیید اتصال PostgreSQL از محیط Function را باز اعلام می‌کند. بنابراین «deployment completed» به معنی تأیید سلامت runtime نیست.

**هیچ جدول یا داده اختصاصی MegaMarket در شاخه production مشاهده نشد.** جداول و Function دفتر کارخانه متعلق به TRADIX هستند و نباید بدون طراحی جداسازی محصول، مستقیماً به مخزن داده MegaMarket تبدیل شوند.

### Backblaze B2

اجرای GitHub Actions با شناسه [43745900128](https://github.com/grinlife4-stack/TRADIX/actions/runs/43745900128) موفق بوده است:

- احراز هویت و دسترسی Bucket: موفق
- نوشتن و خواندن مجدد شیء آزمایشی: موفق
- شیء health-check به‌علت سیاست نسخه‌بندی حذف خودکار نشده است.

پس اتصال B2 برای آزمون ذخیره‌سازی تأیید شده است. این فقط زیرساخت ذخیره‌سازی کارخانه است؛ اتصال داده بازار MegaMarket محسوب نمی‌شود. وضعیت قدیمی مستندات که اتصال B2 را «تأییدنشده» می‌دانست باید در بازبینی بعدی به‌روزرسانی شود.

### Railway

اتصال حساب و Workspace تأیید شد، اما Workspace شخصی در حال حاضر **صفر پروژه** دارد. هیچ سرویس یا deployment برای TRADIX یا MegaMarket مشاهده نشد.

### Cloudflare

حساب متصل است، اما در حساب بررسی‌شده:

- Zone و دامنه‌ای ثبت نشده است.
- Worker، Pages، D1، Queue، Workflow، KV، Vectorize و Durable Object وجود ندارد.
- R2 هنوز فعال نشده است.
- دسترسی به Cloudflare Containers به طرح پولی نیاز دارد و در دسترسی فعلی قابل استفاده نبود.

در نتیجه Cloudflare در حال حاضر زیرساخت اجرایی MegaMarket نیست.

## 6. قابلیت‌های عمومی TRADIX که بیرون از main وجود دارند

شاخه‌ها و PRهای کارخانه شامل طراحی و پیاده‌سازی‌های آزمایشی برای قراردادهای Task/Mission/Model، دفتر رخداد، Memory Gateway، Worker Lease/Fencing، Evidence Manifest، Docker/gVisor sandbox، کنترل‌های پیش‌اجرا و طرح Hardware Resource Manager هستند.

بخش‌هایی از این کارها CI موفق دارند، اما هنوز در `main` ادغام نشده‌اند. برای مثال PR مربوط به Hardware Resource Manager شامل مشخصات و schemaهای سخت‌افزار است؛ این را نباید با یک مدیر سخت‌افزار عملیاتی و متصل به دستگاه‌ها اشتباه گرفت.

نتیجه: TRADIX از نظر طراحی و نمونه‌های آزمایشی جلوتر از `main` است، اما «قابلیت موجود در شاخه» با «قابلیت یکپارچه، قابل‌استفاده و runtime-verified» یکسان نیست.

## 7. تصمیم‌های ایمنی و ادغام

تا زمان تعیین تکلیف:

1. هیچ‌یک از PRهای #24 تا #30 ادغام نشوند.
2. کد دراپ‌شیپینگ حذف نشود؛ در شاخه‌های خودش باقی بماند و فقط اجزای عمومی آن بعداً جداگانه ارزیابی شوند.
3. دو مسیر `products/megamarket` و `products/mega-market` به دو پرونده محصول تبدیل نشوند؛ مسیر مصوب فعلی همان `products/megamarket` است.
4. برای MegaMarket در Neon production جدول نسازیم و هیچ migrationای اجرا نکنیم.
5. سرویس پولی جدید یا deployment جدید ایجاد نکنیم.
6. هیچ داده‌ای بدون بررسی مجوز دریافت، ذخیره، تحلیل یا نمایش داده نشود.
7. رتبه‌بندی هرگز به نرخ کمیسیون دسترسی نداشته باشد.

## 8. اقدام بعدی واحد

**فاز صفر واقعی MegaMarket را اجرا کنیم: انتخاب یک دسته محصول و یک بازار آغازین، سپس اعتبارسنجی یک یا دو منبع داده مجاز برای همان محدوده.**

تا وقتی دسترسی قانونی، پایدار و اقتصادی به داده واقعی ثابت نشده، ساخت UI، موتور رتبه‌بندی کامل یا زیرساخت سنگین زودهنگام است. پس از تأیید منابع، مدل کاتالوگ و شواهد خریدارمحور طراحی می‌شود؛ نه مدل سودآوری فروشنده.

## 9. محدودیت این ممیزی

این گزارش بر وضعیت قابل‌مشاهده GitHub، Neon، Railway و Cloudflare در زمان ممیزی متکی است. مقادیر محرمانه، secretها یا محتوای credentialها خوانده یا ثبت نشده‌اند. سلامت HTTP تابع `memorygw` از این محیط قابل تأیید نبود. کد شاخه‌های آزمایشی بررسی شد، اما اجرای محلی کامل آن‌ها در این محیط ممکن نشد؛ نتیجه تستی که به آن استناد شده، اجرای واقعی GitHub Actions است.

**خلاصه وضعیت:** اسناد محصول موجود؛ کد MVP مصوب غایب؛ کد فروشنده‌محور آزمایشی و ادغام‌نشده؛ داده واقعی و مجوز منبع هنوز فراهم نشده؛ زیرساخت تولید MegaMarket ایجاد نشده است.
