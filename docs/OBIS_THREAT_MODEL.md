# OBIS — Threat Model and Security Design Baseline

**Document ID:** OBIS-SEC-THREAT-001  
**Status:** Draft threat model / review required  
**Version:** 0.1.0  
**Related specification:** [OBIS Specification](OBIS_SPECIFICATION.md)  
**Scope:** OBIS-capable Bridge instances and their peer relationships  
**Effective date:** 2026-11-20

## 1. Purpose

This document identifies the security assets, trust boundaries, adversaries, abuse cases, and minimum mitigations relevant to OBIS. It is a design baseline for selecting concrete security profiles. It is not a completed penetration test, formal risk assessment, or production security certification.

The threat model assumes independently administered peers, potentially untrusted networks, different operators, and the possibility that one peer or Bridge may be compromised while others remain trustworthy.

## 2. Security objectives

An OBIS deployment must preserve:

1. **Confidentiality:** only authorized parties can read protected messages and data.
2. **Integrity:** messages, identities, authorization context, and consequential results cannot be altered undetectably.
3. **Authenticity:** each request and response can be attributed to the correct peer and principal.
4. **Authorization:** a valid identity receives only explicitly approved capabilities and data scopes.
5. **Freshness:** expired, replayed, or stale messages cannot trigger unintended effects.
6. **Availability and containment:** overload or compromise of one peer/Bridge does not automatically disable or compromise unrelated peers.
7. **Accountability:** security-relevant actions produce attributable evidence without leaking secrets.
8. **Owner autonomy:** owners can revoke trust, rotate credentials, export evidence, replace operators, and continue without BRIDEX/TRADIX services.

## 3. Assets to protect

| Asset | Security concern | Primary control owner |
|---|---|---|
| Peer and Bridge identities | Spoofing, impersonation, substitution | Respective peer/Bridge owner |
| Credentials, keys, tokens | Theft, misuse, persistence after revocation | Credential issuer and owner |
| Capability permissions and scopes | Privilege escalation, confused deputy | Receiving peer |
| Payloads and business data | Disclosure, tampering, unauthorized reuse | Data-owning peer |
| Bridge source and build chain | Malicious code, dependency compromise | Bridge owner and maintainer |
| Configuration and mappings | Endpoint redirection, unsafe transformation | Bridge owner |
| Local queues and state | Tampering, replay, loss, unauthorized access | Bridge operator/owner |
| Audit and evidence records | Deletion, alteration, repudiation, leakage | Record owner |
| Availability and compute capacity | Flooding, resource exhaustion, queue saturation | Each operator |
| Protocol/schema definitions | Downgrade, ambiguity, parser confusion | OBIS specification steward and implementers |

## 4. Trust boundaries

The design must explicitly model these boundaries:

- **Peer-to-peer network boundary:** all network input is untrusted until authenticated, validated, and authorized.
- **Bridge process boundary:** a Bridge must not gain unrestricted access to its host or adjacent services.
- **Owner/operator boundary:** an operator may run a Bridge without owning its data, source, or policy authority.
- **Credential boundary:** secret material is held by the owner-approved secret manager or secure runtime, not embedded in source or protocol metadata.
- **Data-owner boundary:** the peer that owns data decides which fields, purposes, and operations may cross its boundary.
- **Intermediary boundary:** proxies, gateways, queues, and relays are additional trust domains and must be explicitly configured and audited.
- **BRIDEX/TRADIX boundary:** generation and internal engineering services are not runtime trust authorities for OBIS.

No trust boundary may be removed merely because two components belong to the same portfolio or were generated by the same factory.

## 5. Adversary model

The design considers:

- An unauthenticated internet or network attacker.
- A malicious or compromised authenticated peer.
- A compromised Bridge process or host.
- A malicious insider or over-privileged operator.
- A stolen, leaked, expired-but-still-accepted, or improperly scoped credential.
- A compromised dependency, build system, package, or update channel.
- A replaying, delaying, duplicating, or reordering intermediary.
- A denial-of-service actor targeting parsing, queues, expensive operations, or authentication.
- A confused-deputy attack in which a Bridge uses its own privileges on behalf of an unauthorized caller.

OBIS cannot guarantee security if the owner-controlled endpoint, host, identity issuer, or signing keys are fully compromised. It must nevertheless limit lateral movement, scope damage, support revocation, and preserve evidence where possible.

## 6. Threats and required mitigations

### 6.1 Spoofing and impersonation

**Threat:** An attacker claims to be a trusted peer, Bridge, owner, or principal.

**Required controls:**
- Authenticate the remote peer using a declared security profile.
- Bind authenticated credentials to the expected peer identity.
- Keep peer, Bridge, owner, operator, and principal identities distinct.
- Reject identity mismatch and invalid trust chains.
- Do not treat a network address, catalog entry, or self-asserted identifier as proof of identity.

### 6.2 Unauthorized access and privilege escalation

**Threat:** A valid peer invokes an unapproved capability, expands scopes, or accesses fields outside its grant.

**Required controls:**
- Enforce authorization at the receiving peer for every capability.
- Apply default-deny and least privilege.
- Bind grants to principal, peer, capability, data scope, and expiry.
- Re-check authorization for consequential operations.
- Make revocation effective within a documented bounded interval.
- Capability negotiation must never grant permission.

### 6.3 Tampering and message substitution

**Threat:** An attacker modifies payloads, recipient, capability, scope, expiry, or response data.

**Required controls:**
- Protect the transport channel against in-transit modification.
- Where messages cross untrusted intermediaries or require durable proof, define a signed-message/evidence profile.
- Bind security-relevant envelope fields to the authenticated context.
- Validate schemas and reject ambiguous duplicate fields or parser differentials.
- Correlate responses to the original request and authenticated peer.

### 6.4 Replay and stale operations

**Threat:** A previously valid request is resent to repeat an action or use an expired grant.

**Required controls:**
- Require unique message identifiers and bounded expiry/deadlines.
- Define clock-skew tolerance and freshness validation.
- Track replay identifiers for the required retention window.
- Require idempotency keys for retryable state-changing operations.
- Reject expired credentials and grants.
- Provide status/evidence reconciliation when an operation outcome is unknown.

### 6.5 Information disclosure

**Threat:** Payloads, metadata, error messages, logs, capability lists, or audit records reveal protected information.

**Required controls:**
- Encrypt transport using a production-approved profile.
- Minimize payload and metadata disclosure.
- Apply data classification and field-level authorization.
- Do not return raw stack traces, secrets, internal paths, or protected-resource existence details.
- Redact credentials and sensitive payloads from logs and evidence.
- Define retention and deletion obligations with the data owner.

### 6.6 Denial of service and resource exhaustion

**Threat:** Oversized messages, expensive parsing, connection floods, retries, or queue growth exhaust resources.

**Required controls:**
- Set bounded message size, nesting depth, processing time, concurrency, and queue capacity.
- Apply rate limits and backpressure by peer and capability.
- Use bounded retries and circuit breaking where appropriate.
- Avoid expensive work before authentication and basic validation.
- Separate health/readiness from expensive business operations.
- Ensure one peer cannot exhaust resources reserved for unrelated peers.

### 6.7 Confused deputy and unsafe capability execution

**Threat:** A Bridge uses its own authority to execute a request the caller is not allowed to make.

**Required controls:**
- Preserve original caller/principal attribution through every hop.
- Do not substitute Bridge identity for caller identity in authorization decisions.
- Do not expose generic shell, code execution, unrestricted filesystem, database, or network proxy capabilities.
- Validate the operation against both caller grant and Bridge owner policy.
- Require explicit approval for irreversible, financial, or externally consequential actions.

### 6.8 Configuration and endpoint substitution

**Threat:** An attacker or faulty update redirects a Bridge to an attacker-controlled peer, changes mappings, or broadens allowed scopes.

**Required controls:**
- Treat peer endpoint, trust anchor, mapping, and scope changes as privileged configuration changes.
- Require owner-authorized change control and attributable audit records.
- Validate peer identity after connection, not merely the configured address.
- Support configuration export, integrity verification, rollback, and recovery.
- Separate per-Bridge configuration; never share destination secrets or mappings by default.

### 6.9 Supply-chain and update compromise

**Threat:** Malicious dependencies, build tools, packages, or release artifacts compromise a Bridge.

**Required controls:**
- Maintain dependency manifests and license inventory.
- Produce reproducible or verifiable builds where feasible.
- Sign release artifacts under owner-controlled or owner-approved signing authority.
- Record source revision and build provenance.
- Scan dependencies and artifacts before release.
- Allow the owner to rebuild or fork independently of BRIDEX services.
- Define rollback and revocation for compromised releases.

### 6.10 Audit tampering and repudiation

**Threat:** An actor deletes or alters evidence of authorization, requests, or state-changing operations.

**Required controls:**
- Record attributable security decisions and consequential operations.
- Protect audit records from unauthorized modification and deletion.
- Separate operational logs from durable audit evidence where required.
- Use integrity protection and trusted timestamps appropriate to the selected profile.
- Keep evidence under owner-controlled or mutually agreed storage.
- Do not make a central TRADIX or BRIDEX audit service mandatory.

## 7. Security invariants

Every conforming production implementation must preserve these invariants:

1. No authenticated identity is automatically authorized.
2. No capability declaration is an authorization grant.
3. No portfolio relationship creates implicit trust.
4. No Bridge may use its own authority to bypass the caller's scope.
5. No external OBIS request requires TIIS, TRADIX, or BRIDEX.
6. No unbounded input, retry, queue, or execution path is accepted.
7. No secret value is stored in source, public metadata, or ordinary audit records.
8. Revocation and disablement must be possible under the owner's control.
9. A Bridge compromise must not automatically grant access to other Bridge instances or peer systems.
10. Security controls must remain operable after ecosystem separation.

## 8. Initial risk register

| Risk | Initial severity | Required treatment before production |
|---|---|---|
| Identity spoofing or credential theft | Critical | Select and test mutual-authentication profile |
| Scope escalation/confused deputy | Critical | Define authorization token/context binding and negative tests |
| Replay of state-changing requests | High | Define replay store, expiry, idempotency, and reconciliation |
| Compromised Bridge host | Critical | Process isolation, least privilege, secret protection, containment |
| Malicious dependency/build artifact | High | Provenance, dependency controls, artifact verification |
| Data leakage through logs/errors | High | Redaction, schema minimization, audit review |
| Denial of service | High | Explicit resource bounds and rate-control profile |
| Unsafe intermediary behavior | High | Define trust, signature, and attribution rules for relays |
| Incompatible or ambiguous schemas | Medium/High | Final schema dialect, strict validation, conformance tests |
| Loss of TRADIX/BRIDEX services | Medium | Independent operation and exit test |

Severity is preliminary and must be recalculated against actual deployment context, data sensitivity, and business impact.

## 9. Required security profiles before OBIS 1.0.0

The following profiles must be designed and tested before a production release:

- **Peer authentication profile:** credential type, identity binding, mutual-authentication behavior, trust anchors, expiry, rotation, revocation.
- **Transport protection profile:** confidentiality, integrity, server/client authentication, protocol versions, downgrade prevention.
- **Authorization context profile:** principal, peer, capability, scope, audience, expiry, delegation, and revocation semantics.
- **Message integrity/evidence profile:** whether and when end-to-end message signatures are required, canonicalization, key ownership, timestamping, and verification.
- **Replay/idempotency profile:** nonce/message retention, clock skew, idempotency scope, and duplicate outcome behavior.
- **Intermediary profile:** trust and attribution rules when a proxy, broker, queue, or relay is explicitly used.
- **Operational hardening profile:** process isolation, secret handling, rate limits, audit protection, backup, recovery, and incident response.

No cryptographic suite is selected by this draft. Selection must be evidence-based and documented in a separate versioned profile; implementers must not infer a production-approved algorithm from this threat model.

## 10. Minimum negative test scenarios

The conformance suite must verify rejection or safe containment for:

- Unknown peer and mismatched peer identity.
- Valid authentication but missing capability permission.
- Expired or revoked credential/grant.
- Capability or scope altered after authorization.
- Expired, duplicated, or replayed message.
- Oversized, deeply nested, malformed, or schema-ambiguous payload.
- Unsupported required protocol version/profile.
- Attempted generic command or unrestricted resource operation.
- Unauthorized field disclosure.
- Duplicate state-changing request and idempotency-key conflict.
- Timeout where remote outcome is unknown.
- Malicious or unavailable intermediary.
- Compromised/invalid package signature or dependency provenance.
- BRIDEX/TRADIX unavailable while independent OBIS peer communication is exercised.

## 11. Residual risks and limits

- OBIS cannot make a compromised endpoint trustworthy.
- A malicious authorized peer may misuse the exact data and capabilities it legitimately receives; contractual, monitoring, and revocation controls remain necessary.
- Clock-based expiry depends on bounded clock accuracy; the chosen profile must define skew and failure behavior.
- End-to-end signatures, transport security, and audit evidence solve different problems and are not interchangeable.
- A secure protocol does not by itself make a business workflow, payment, financial operation, or domain policy safe.
- Regulatory, privacy, and sector-specific controls must be assessed separately for each deployment.

## 12. Review gate

Before selecting the first production security profile, review this threat model against:
- Actual OBIS peer and Bridge deployment topology.
- Data classifications and consequential operations.
- Owner/operator/maintainer separation.
- Credential issuance, storage, rotation, and revocation.
- Direct and intermediary communication paths.
- Incident response and independent exit requirements.

The threat model must be revised when these facts change. OBIS 1.0.0 must not be approved until the security profiles, negative tests, and independent interoperability tests pass.

## 13. Governing security statement

**OBIS assumes no implicit trust. Each peer controls its own data and permissions; each Bridge owner controls its own implementation and credentials; and compromise or removal of BRIDEX/TRADIX must not become a path to compromise or disable independent peers.**
